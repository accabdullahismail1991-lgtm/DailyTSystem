# واجهة API وسيطة لربط النظام المحاسبي بـ Power BI

هذا مشروع Firebase Cloud Functions منفصل تماماً عن `accounting.html` — يقرأ نفس بيانات
النظام المحفوظة سحابياً بـ Firestore (عبر `cloud-sync.js`) ويعرضها كجداول JSON منظَّمة
عبر روابط HTTP يستطيع Power BI الاتصال بها مباشرة (Get Data ← Web).

**لن يعمل شيء تلقائياً** — يجب نشر هذه الدالة يدوياً من حساب Firebase الخاص بك أولاً.

## المتطلبات قبل البدء

1. حساب Firebase على نفس المشروع الذي يستخدمه `cloud-sync.js` حالياً
   (`accounting-and-dailytsystem`)، **مرتقّى لخطة Blaze** (دفع حسب الاستخدام) — Cloud
   Functions لا تعمل إطلاقاً على الخطة المجانية Spark، بخلاف Firestore نفسه. هذه نفس
   الترقية التي سبق التوصية بها لحل مشكلة استنفاد حصة الكتابة اليومية، فتُفيد الغرضين معاً.
2. [Node.js](https://nodejs.org) (نسخة 20 أو أحدث) و npm مثبَّتان على جهازك.
3. أداة سطر أوامر Firebase:
   ```bash
   npm install -g firebase-tools
   firebase login
   ```

## خطوات النشر

من داخل مجلد `powerbi-api` (وليس جذر المستودع):

```bash
cd powerbi-api
firebase use accounting-and-dailytsystem   # تأكّد أنه نفس معرّف مشروعك — عدّل .firebaserc إن اختلف
cd functions
npm install
cd ..
```

عيّن مفتاح API سرياً (اختر قيمة طويلة عشوائية بنفسك، واحتفظ بها — ستحتاجها لاحقاً بـ Power BI):

```bash
firebase functions:config:set powerbi.apikey="ضع-هنا-مفتاحاً-سرياً-طويلاً-من-اختيارك"
```

ثم انشر:

```bash
firebase deploy --only functions
```

سيظهر بنهاية النشر رابط الدالة، بالشكل:
```
https://<region>-accounting-and-dailytsystem.cloudfunctions.net/powerbi
```
احتفظ بهذا الرابط.

## الاتصال من Power BI

1. Power BI Desktop ← **Get Data** ← **Web**.
2. أدخل الرابط الكامل لأحد النقاط أدناه (مثال: `.../powerbi/trialBalance?company=default`).
3. عند الطلب، اختر **Advanced** لإضافة ترويسة HTTP:
   - الاسم: `x-api-key`
   - القيمة: نفس المفتاح السري الذي عيّنته أعلاه
4. اضغط OK — يجب أن تظهر البيانات كجدول JSON قابل للتحويل مباشرة (Power Query سيعرض
   `List`/`Record` تحتاج "To Table" ثم "Expand" — الخطوات المعتادة لأي مصدر JSON بـ Power BI).
5. كرّر لكل نقطة نهاية تحتاجها كجدول منفصل، ثم اربط الجداول ببعضها داخل نموذج Power BI
   (accountCode في `entries`/`trialBalance` يطابق code في `accounts`، وهكذا).

## نقاط النهاية (Endpoints) المتاحة

جميعها تتطلب ترويسة `x-api-key`، وتقبل `?company=` اختيارياً (القيمة الافتراضية `default`
للشركة الرئيسية؛ لأي شركة أخرى استخدم نفس معرّفها كما يظهر بشاشة "إدارة الشركات" بالنظام).
النقاط التي تحتوي حركات تقبل أيضاً `?from=YYYY-MM-DD&to=YYYY-MM-DD` لتصفية الفترة.

| النقطة | الوصف |
|---|---|
| `GET /accounts` | دليل الحسابات الكامل (الرمز، الاسم، النوع، الحساب الأب، رصيد افتتاحي، تصنيفا التدفقات/الميزانية) |
| `GET /costCenters` | مراكز التكلفة |
| `GET /projects` | المشاريع |
| `GET /branches` | الفروع |
| `GET /entries` | القيود التفصيلية — سطر واحد لكل بند مدين/دائن، مع رمز الحساب والفرع المُحتسَب لكل قيد |
| `GET /trialBalance` | ميزان مراجعة: رصيد افتتاحي + حركة الفترة + رصيد ختامي لكل حساب طرفي |
| `GET /branchReport` | ملخص حركة كل فرع (عدد الحركات، إجمالي مدين/دائن، صافي) |

## لماذا لا توجد نقطة نهاية لقائمة الدخل/الميزانية/التدفقات النقدية جاهزة؟

هذه التقارير بالنظام الأصلي تعتمد منطقاً محاسبياً معقَّداً ومتراكماً (تصنيف متداول/غير
متداول، معالجة المخصصات، طريقة التدفقات النقدية غير المباشرة...) لو أُعيد بناؤه هنا بمعزل
عن الكود الأصلي، سيحتاج تحديثاً يدوياً متزامناً مع كل تعديل مستقبلي على تلك القواعد داخل
`accounting.html` — وإلا اختلفت النتائج بصمت بين ما يعرضه التطبيق وما يعرضه Power BI.

البديل الأسلم والأنسب لطبيعة Power BI أصلاً: استخدم `/accounts` و`/entries` (تحتوي كل ما
يلزم: نوع الحساب، تصنيفا التدفقات/الميزانية، رمز الفرع) كجداول أساسية، وابنِ القياسات
(DAX Measures) داخل Power BI نفسه — هذا هو الاستخدام المُصمَّم له BI أصلاً، ويمنحك مرونة
أكبر لاحقاً (فترات مقارنة، شرائح تفاعلية...) لا يوفرها تقرير جاهز مُصدَّر كأرقام نهائية.

## ملاحظة أمان

هذه بيانات محاسبية حقيقية. لا تشارك رابط الدالة أو مفتاح `x-api-key` مع أي طرف لا تثق به،
ولا تُثبِّت المفتاح داخل ملف Power BI (`.pbix`) إن كنت ستشارك الملف مع آخرين — استخدم
معامل Power BI (Parameter) للمفتاح بدلاً من كتابته مباشرة بعنوان URL الثابت.
